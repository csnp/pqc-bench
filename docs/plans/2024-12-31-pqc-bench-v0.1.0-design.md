# PQC-Bench v0.1.0 Design Document

**Status:** Approved
**Author:** CSNP
**Date:** 2024-12-31

---

## Executive Summary

PQC-Bench is an intelligent benchmarking and recommendation engine for Post-Quantum Cryptography. Unlike existing tools that dump raw performance data, PQC-Bench translates developer constraints into actionable recommendations with full reasoning and citations.

**Mission:** Make PQC adoption accessible by providing answers, not data.

---

## Design Principles

### 1. Security as Foundation

- Default to NIST Level 3 (not Level 1) - prioritize security over performance
- Warn explicitly about non-constant-time algorithms
- Never recommend algorithms with known pitfalls without clear warnings
- No "disable security" flags

### 2. Intelligence, Not Pattern Matching

- **Contextual understanding**: "banking" implies compliance requirements
- **Multi-factor reasoning**: Balance actual tradeoffs, not just "fastest"
- **Protocol awareness**: Understand TLS differs from JWT differs from file encryption
- **Explains reasoning**: Users learn as they use the tool

### 3. Comprehensiveness as Credibility

| Dimension | Coverage |
|-----------|----------|
| Algorithms | All NIST standards + serious candidates (BIKE, HQC, Classic McEliece) |
| Security levels | 1, 2, 3, 5 with nuanced guidance |
| Platforms | x86 (AVX2/512), ARM (NEON), WASM, embedded, mobile |
| Use cases | TLS, JWT, SSH, VPN, S/MIME, code signing, blockchain, file encryption |
| Compliance | FIPS 140-3, CNSA 2.0, Common Criteria, PCI-DSS |
| Migration | From RSA, ECDSA, ECDH, Ed25519 |
| Libraries | liboqs, BoringSSL, AWS-LC, OpenSSL 3.x, wolfSSL |

### 4. Honest Engineering

- Every performance claim includes methodology and source
- Acknowledge uncertainty where it exists
- Versioned recommendations that evolve with standards

## Architecture

### Knowledge Layers

```
┌─────────────────────────────────────────────────────────────────┐
│ LAYER 1: STANDARDS & COMPLIANCE                                 │
│ NIST FIPS 203/204/205, CNSA 2.0, FIPS 140-3, Common Criteria   │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│ LAYER 2: ALGORITHM PROFILES                                     │
│ Security properties, performance by platform, requirements,     │
│ compliance status, implementation availability                  │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│ LAYER 3: USE CASE TEMPLATES                                     │
│ TLS handshakes, JWT tokens, file encryption, key exchange       │
│ Protocol-specific constraints and priorities                    │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│ LAYER 4: PLATFORM PROFILES                                      │
│ AWS Lambda, iOS, Android, embedded devices, browsers            │
│ Hardware capabilities, typical constraints                      │
└─────────────────────────────────────────────────────────────────┘
```

### Recommendation Pipeline

```
STAGE 1: PARSE & ENRICH
User query → Extract explicit constraints → Infer implicit constraints

STAGE 2: FILTER (Hard Requirements)
All algorithms → Apply hard filters → Candidate set

STAGE 3: SCORE (Soft Preferences)
Candidates → Multi-factor scoring with context-dependent weights → Ranked list

STAGE 4: RANK & EXPLAIN
Ranked list → Generate explanations with citations → Recommendation output
```

## Data Model

### Algorithm Profile (Core Schema)

```python
@dataclass
class AlgorithmProfile:
    # Identity
    id: str                          # "ml-kem-768"
    family: str                      # "ML-KEM"
    variant: str                     # "768"
    names: AlgorithmNames            # FIPS name, legacy name, OID, TLS codepoint

    # Security
    security: SecurityProfile        # Level, bits, properties, caveats, citations

    # Compliance
    compliance: ComplianceProfile    # NIST status, FIPS validation, framework approvals

    # Performance
    performance: Dict[str, PlatformPerformance]  # By platform, with methodology

    # Sizes
    sizes: SizeProfile               # Keys, ciphertext/signature, with comparisons

    # Requirements
    requirements: ImplementationRequirements  # FPU, stack, constant-time, libraries
```

### Key Supporting Types

```python
@dataclass
class SecurityCaveat:
    severity: str                    # "info", "warning", "critical"
    description: str
    mitigation: Optional[str]
    reference: str                   # URL or paper citation

@dataclass
class BenchmarkMethodology:
    library: str                     # "liboqs 0.10.0"
    compiler: str                    # "clang 17.0.0 -O3"
    cpu: str                         # "Intel Xeon Platinum 8375C"
    date: str                        # "2024-12"
    iterations: int
    source: str                      # URL to reproducible benchmark

@dataclass
class FrameworkApproval:
    framework: str                   # "CNSA 2.0", "FIPS 140-3"
    status: str                      # "approved", "recommended", "pending"
    level: Optional[str]             # "Secret", "Top Secret"
    effective_date: Optional[str]
    notes: Optional[str]
```

## CLI Design

### Command Structure

```
pqc-bench
├── recommend    Primary command (also default)
├── explain      Deep dive on one algorithm
├── compare      Side-by-side comparison
├── migrate      Migration guidance from classical
├── compliance   Framework-specific requirements
└── version/help
```

### Output Tiers

1. **Quick** (default): 3-4 lines with recommendation and key reason
2. **Verbose** (`--verbose`): Full box with analysis, alternatives, citations
3. **Machine** (`--json`): Structured JSON for CI/CD integration

### Output Principles

- Most important info in first 3 lines (scannability)
- Primary recommendation in visual box, alternatives as plain text
- Every output ends with actionable next step
- Citations always visible (credibility)
- No color-only information (accessibility)

## Success Criteria

1. **Useful**: A developer can describe their use case and get a valid recommendation in <5 seconds
2. **Credible**: Every recommendation includes citations to authoritative sources
3. **Honest**: Limitations and caveats are surfaced, not hidden
4. **Extensible**: Adding a new algorithm requires only data, not code changes
